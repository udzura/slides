【日本語版】 それが作られた時代 - SmartHRのアプリケーションは2015年2月にファーストコミット - ActiveStorage以前の世界

【日本語版】 それから9年 - 一度Paperclipから移行しつつ、CarrierWaveを使い続けて9年 - Uploaderクラス: 32 - `mount_uploader`: 87箇所 - 1モデルに最大8個の画像 - CarrierWaveは古いバージョンで、更新には既存仕様との互換性整理が必要 【メモ】 移行の経緯: 2017年5月にPaperclipからCarrierWaveへ移行し、2017年11月にPaperclipを削除（質疑用） 他のライブラリ、特にRuby・Rails本体は常にほぼ最新を維持している。今回の更新の難しさは、CarrierWaveと当社の既存仕様の互換性に関する話。

【日本語版】 症状 - パスの計算ロジックが複雑化し、何度も壊れた - 実際に、ファイルアップロード起因の障害が何度も起きていた - サイズ違い画像（`version`）を同期的に生成している - アップロード時にEXIFを同期処理している - アップロードを制御できない（履歴分割で大量に走る） - 画像の仕様が、CarrierWave側もSmartHR側も複雑で更新できない

課題が塊になっている。分解しないといけない。

【日本語版】 3つの性質に優先順位をつける 1. 信頼性（Reliability）: パスが不安定で障害が起きやすい → まずファイルの参照を安定させる 2. 利用容易性（Usability）: 性能・開発生産性 → アップロードを速くする 3. 保守性（Maintainability）: バージョンアップが難しい → 今日は少しだけ触れる 【メモ】 お客様が実際に感じている障害と遅さから先に手を付けた。保守性は3番目で、今日は後半で少しだけ扱う。 セキュリティは前面に出さない（WAFなどの多層防御があることは質疑用。ライブラリ更新の代わりになるという意味ではない）。

発表の地図。主役はパスと履歴。3番目の保守性（依存整理）は、後半で少しだけ扱う補足的な展望。

今回扱う参照障害についての説明。参照のためのデータが壊れたもので、ファイル自体が消えた事例はない。過去の障害への対応完了と、再発防止のための構造改善の展開状況を区別する。

CarrierWaveの概念的な流れ。assign時にcache!が走る場合がある。正確なコールバック順序を示すものではない。

【日本語版】 CarrierWave：書き込み 【メモ】 図のCache IDは再開用のcache_nameを指す（cache_id / original_filename）。モデルのIDとは別。 画像の永続化とidentifierのDB保存は役割を示した概念図で、厳密なコールバック順序ではない。

【日本語版】 CarrierWave：読み出し・参照 【メモ】 identifierはランダムなIDを新規発行する意味ではない。 retrieve_from_store!は参照の復元で、常に画像の全バイトを取得するわけではない。 参考: https://github.com/carrierwaveuploader/carrierwave/tree/master/lib/carrierwave/uploader

【日本語版】 ファイルパスは簡単に上書きできる - `store_dir` メソッドで上書きできる - テナントIDやテーブル名など、モデルの情報を含められる - モデルの状態やメソッドの変更が、パスの壊れやすさにつながる （コード） 【メモ】 コードは抽象化したもの

【日本語版】 複雑さゆえに: 時刻によるif文 （コード） - パスをスナップショットとして持たないので、**ロジックを変えられない** 【メモ】 振り分けの基準は created_at ではなく「更新日時」。話すときも更新日時と言う。

【日本語版】 cache_path の固定 - cacheしてからstoreするまでの間に、cache pathの計算結果が変わる - 例: IDがある／ないでパスが変わる実装 - 過去に、この原因で複数回の障害があった - 対策: cache時のパスを保存し、取り出すときは再計算しない

【日本語版】 変更以前 【メモ】 - ID発行されるのに、retrieveで複雑な計算があった - ID発行の前後でそのロジックが変わると... - ID → cache_path は一意に引けないとダメでは？

【日本語版】 変更以後 【メモ】 - cache作成のタイミングで、ID → cache_pathをRedisに保持 - 取り出すときは再計算せず、Redisから取得 - シンプルに！ - cache IDはフォームが持つので、提出している本人からは失われない。しかも本人しか知らないIDなので、鍵として安全 - 対応表はあくまでキャッシュなので、1〜2週間ほどで消える。1ヶ月後の再開は対象外（質疑用）

【日本語版】 cache_path 固定の結果 - 改善第一弾として2025年末に完了 - cache_path起因の障害は **ゼロ** になった - 次は、store_path側でも再発を防ぐための構造改善

【日本語版】 次の山は store_path の固定 - identifierの形式を変える案もあったが、**専用のカラム** を導入する方針に - 読むときはそのカラムを優先、なければ従来どおり計算 - 既存データはバックフィル。すべて埋まれば、フォールバックを消せる - 問題の大きいUploaderから始めて、順次広げる

【日本語版】 実装イメージ: 書き込み側 （コード） - store の直後に、パスを専用カラムへ記録する 【メモ】 hanicaのコードからポイントを絞り、若干改変したもの。should_not_store_full_path? が write フラグに相当。

【日本語版】 実装イメージ: 読み込み側 （コード） - 記録がなければ、従来どおり計算したパスを使う - 計算値と記録値の不一致は、ログで観測する 【メモ】 use_persisted_store_path が read フラグに相当。次の「戻せる設計」へのつなぎ。

【日本語版】 write / read の2フェーズフラグ | ステップ | write | read | 備考 | | 1 | 一部ON | OFF | 一部テナントでdouble write。参照は従来どおり | | 2 | _全体ON_ | OFF | 全体でdouble write。参照は従来どおり | | 3 | _全体ON_ | 一部ON | 一部テナントでdouble writeした固定パスによる参照を開始 | | 4 | _全体ON_ | _全体ON_ | 全体で固定パスによる参照へ切り替え |

フラグがあるだけで安全とせず、戻した場合の挙動も検証する。

定期同期したBigQueryのデータに、毎日クエリを投げて監視した。 実際のクエリ（Redashの「store_path不整合チェック」、毎日22:30実行）を簡略化し、テーブル名・データセット名は伏せたもの。 見ているのは3種類の不整合: ファイルがあるのにパスがない／パスがあるのにファイルがない／パスの末尾がファイル名と一致しない。 実際のクエリでは、調査済みで既知の行を除外している。

【日本語版】 Step 2: AIがシナリオにして、実行する 【メモ】 構造化の形式はGherkinなどもあるが、今回は独自形式。 実行役のAIをAIの中で起動。やり取りはファイルとスキーマ。 図は次のStep 3まで含めた全体像。観測と判定を分け、人が最後に証跡をレビューする。 コンパイラのpassのように、各段階が成果物を次へ渡す。

【日本語版】 store_path 固定の現在地 - 一部の画像では、固定パスへ **完全に切り替わった** - 同じ手法で、少しずつ全画像に広げていく

従業員の履歴情報も画像も重要。両方を組み合わせると、ファイルのライフサイクルに注意が必要。

【日本語版】 バイテンポラルデータモデル 【メモ】 日付は説明用。期間は開始を含み終了を含まない [from, to)。 行Aのtransaction_toを更新時刻で閉じ、行B・Cを追加する。旧行を削除して2行にするわけではない。 参考: https://github.com/kufu/activerecord-bitemporal

【日本語版】 バイテンポラルとファイルの困り事 - 履歴分割のたびに、同じファイルを持つ行が複製される - 実装的には「前の履歴」の値コピー - ところがCarrierWaveは、**値を代入しただけでアップロード（`cache!`）が走る** - 見えない副作用として、不要なアップロードが走ってしまう

【日本語版】 もう一つの性能改善: 再アップロードを防ぐ - 履歴を複製するときに **「履歴複製中」のマーク** を付ける - その間はアップロードを回避し、同じファイルを再アップロードしない - フック内部へ状態を伝えるため、`CurrentAttributes` を使う - 本番投入間近のPRとして実装済み

簡略化した模擬コード。既存の VersionCacheSuppressible（承認処理中だけ version 生成を止める仕組み）と同じ形で、 CurrentAttributes でスコープを示し、CarrierWave のフック（cache!）を上書きして抑止し、ensure で必ず解除する。 リリース間近の実際のPRは別の形（同じリクエスト内で同じ store path への2回目の保存を省く）で、細部は異なる。

履歴分割時の重複アップロードを抑止する変更は、もうすぐ本番環境に入れられる状態のPRになっている。そのPRを最新のstagingにリベースし、ローカルで計測した。 操作: 実画面から「アバターいますぐ」（承認なし）の申請を提出し、既存のプロフィール画像を差し替える（申請提出 create_by_applicant）。 抑止なし／ありを交互に3回ずつ、毎回別の画像で実行した平均。 全体 17.0秒 → 9.6秒（−44%）。GCS操作 39回 → 22回。put / delete / copy がそれぞれ 11回 → 6回、get / metadata が 3回 → 2回。 1回あたりのレイテンシ（put 約430ms、delete 約300ms、copy 約225〜260ms）は前後で同じなので、短縮分は回数の削減によるもの。 対策後もGCSが全体の約70%を占める。 5章のPoC（設計・調査段階）とは違い、こちらはリリース直前のPR。ただしローカルでの計測であり、本番での効果や展開完了を示すものではない。 コピーした履歴が、期待どおりの画像を参照し続けていることも確認済み。

【日本語版】 この章で紹介する施策は、設計・調査段階にある。 図は目指す責務の境界を示すもので、実装済みの構成ではない。 後述のパフォーマンス計測はローカルPoCによるもので、本番の結果ではない。

現状の責務の絡まりを概念的に表した図。厳密な実行順やデータフローではない。

【日本語版】 複雑性の削減のために目指す姿 【メモ】 計画段階の責務・依存関係の図。矢印は画像データの転送経路ではない。 Uploaderの仕事を「決まったパスにバイト列を置く」ことへ絞り、画像処理を分離する。

既存資料の互換レイヤのコード例を再掲。Before / After は呼び出し側の比較。 present? が依存するUploaderのblank?の挙動を、互換レイヤ内部で維持する。 新しいAPI名だけでストレージ上のファイル実在確認を行うという意味ではない。

SmartHRが必要とする画像操作を互換レイヤで公開し、CarrierWave固有のAPIを内側に閉じ込める。

【日本語版】 画像の「前処理」が非常に多い - 表示用途に合わせたサイズ違い画像（`version`）の生成 - EXIFの向き情報に基づく回転 - EXIF情報（住所など）の除去 - これらがアップロード時に**同期で**走り、保存完了までの待ち時間になる

【日本語版】 同期処理を切り出したい - サイズ違い画像は、別サービスでオンデマンドに生成するとどうか？ - 位置情報の除去など、必要な画像処理を維持することが前提 - 同期処理から何を切り出すかを検討する。EXIF処理を必ず外部へ移すとは限らない - 別サービスの内容はCDNに載せキャッシュすれば、負荷の懸念も小さい - 画像変換サービス + CDN という構成は、実サービスでも多く採られている - Cookpad の [tofu](https://www.slideshare.net/slideshow/20111102-rails-meetuptofu/10084092) を始め、色々 - [ImageFlux](https://imageflux.sakura.ad.jp/) 等専用サービスも 【質疑用】 EXIF処理の計測上の影響は相対的に小さい。既存の実行箇所に維持する可能性もあり、切り出す範囲は検討中。

おまけとしてローカル計測を紹介。申請者による作成処理（create_by_applicant）、3回の平均。 前処理あり17.9秒、なし5.8秒。GCSの往復回数も39→15回。 サイズ違い画像の生成と追加アップロードをやめたため、GCS処理も減るのは自然な結果。 本番の所要時間や改善幅を直接示すものではない。

【日本語版】 複雑な仕様を分析し、必要な振る舞いを明確にする。 CarrierWave固有の操作と画像処理を切り出し、責務の境界を作る。 同期処理の削減はローカルPoCで速度にも効果が見えたが、本番での効果は未確認。 この整理を踏まえて、次章ではCarrierWaveを更新するか置き換えるかを考える。
